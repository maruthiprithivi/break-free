Walkthroughs

Routing

Every run_plan and delegate task may name its own model. Omit it and routing decides which lane — and which model — the task runs on, instead of falling back to defaults.model. Routing is off by default: it changes which model runs your work and what that costs, so it has to be your choice, not an upgrade side effect.

off — the default

An omitted model means defaults.model. No decisions, no calls, no ledger fields. This is what Break Free did before, and it is the escape hatch if routing ever misbehaves.

rules — no key, no network

One ordered regex table. Judgement rules first; then file evidence — if every file a task touches is prose (.md, .txt, .rst, .adoc) it is a prose task, whatever it says; then implementation rules; otherwise fast.

Its "confidence" is invented, so it never gates on a threshold. It escalates only when a task matches the unclear pattern.

jev — TypeSafe System One

Not an LLM. It evaluates typed questions against a state and returns typed answers: a Choice over lanes, a Score for difficulty, and two Nouls for sensitivity and repo context — four questions per task, answered in parallel in one request per plan, so a 12-task plan is one round trip.

Below routing.threshold (default 0.7), or when it answers lead_keeps/unclear, it hands the task back: model comes back null and the task is reported under "Escalated to you". Without a key the plan runs on rules and the result says degraded: <reason> — a router outage never fails a plan.

where you set it — narrower wins

  • Task — model: "..." on the task. Wins over everything; an explicit model is never routed at all.
  • Session — routing: "jev" | "rules" | "off" on the run_plan / delegate call.
  • Environment — BREAK_FREE_ROUTING=jev|rules|off, for every call in that shell or harness session.
  • Project — routing.engine in <repo>/.model-gateway.json, committed and read from the workspace.
  • Global — routing.engine in ~/.config/model-gateway/config.json, for this machine.

a repo cannot turn Jev on behind your back

A committed project file can point a repo at jev, and then everyone who clones it routes through TypeSafe. That is the same egress the file already has through defaults.model — but if you want every routing decision to stay on your machine, set this in your user config, where no repo can reach it:

{ "routing": { "projectMayEnableJev": false } }

Projects may then still ask for rules or off, just not jev. The flag is only ever read from the user config.

60 labeled subtasks (bench/route-set.jsonl); under-routing means a lane cheaper than the one that actually passes verify. The decisions are a recorded live capture replayed offline, so the metrics reproduce — only latency is measured live. "Agreement" means agreement with one author's labels, not with truth. Jev is not "just rules": 71.67% vs 53.33% exact, and 6.98% vs 31.03% under-routing; the rules engine only looks cheaper (64.1% vs 49.4% below all-strong) because it under-routes three times as often, which is the trade the guardrail exists to catch. Routing has not been measured by running real crew work in real repositories — pass rates and calibration need real verify outcomes, which the scorecards collect as they happen.

The tripwire

policy.rules can deny a path and require a review. Both are globs, and both are blind to the one thing that matters most in a diff: what it did to the code inside the file. A worker can "fix" a failing test by deleting the assertion and adding nothing back — the path is untouched, verify goes green, and no glob has an opinion. The tripwire hands the hunks of the worker's diff to Jev and asks five typed questions about what each hunk is.

what it asks — one request per hunk

  • test_weakened — skips, deletes, disables or loosens a test, assertion or lint guard
  • destructive_data — deletes or corrupts stored data
  • security_touch — changes auth, secrets or input validation
  • scope_creep — changes more than the task called for
  • risk — a score, 0 (trivial) to 4 (dangerous), with a confidence

three verdicts

  • block — a hard rejection, with the reason. Only test_weakened ≥ 0.99, destructive_data ≥ 0.99 or risk ≥ 3.5 can block.
  • review — still accepted, but a full review is forced even where the plan would skip it.
  • allow — nothing found.

security_touch and scope_creep never block on their own; a security-touching change is often legitimate, so it escalates rather than rejects.

when it runs — opt-in by path

tripwire.enabled defaults to true, but it only runs for paths a policy.rules entry with action: "check" matches. With no such rule it never runs and costs nothing — the same posture as routing being off by default.

action: "check" is additive: it can add a review or a block, and can never remove a glob-triggered review. An engine that cannot answer reports unknown and never stands in for a review.

Tripwire measured on 175 real merged diffs

4%false flags, 7 of 175 hunks (≤10% target), pass
1%hard-blocked, 1 of 175
96%of clean diffs needed no full review (≥40% target)
309 msp50 latency, 772 ms max (≤500 ms target)
$0.044per 1,000 diffs

That corpus is bench/tripwire-natural.jsonl: 175 hunks from 94 real commits across 3 real repositories. It is all label-clean, and the label is the set's weakness, stated plainly — a merged commit is presumed honest, not known to be, so a commit that weakened a test and got away with it is scored here as a false positive. On the adversarial seeded set (bench/tripwire-set.jsonl, 130 diffs, 30 planted bad) recall is 90% (27/30) and false flags are 14% (14/100) — a miss of the ≤10% target, and swept over the recorded answers no threshold meets both targets there. Zero of those 100 clean diffs were hard-blocked. Nobody has yet run the tripwire against diffs a worker model produced on a real project, which is the distribution it will run in; live answers are not deterministic, so treat a one-diff difference between runs as noise.

The comparison the project loses

The project measured itself against a frontier LLM prompted as a router: the same 60 tasks, the same lane definitions verbatim, the same task facts, batched the way the latency column assumes. Jev lost on judgement.

47.7×faster per decision — the ≥20× clause passes
45.1×cheaper per decision — the ≥50× clause is missed
23.3 pointsbehind on agreement — the ±5-point clause fails
95% vs 71.67%Gemini 3.1 Pro matched the expert labels 95% of the time; Jev matched 71.67%

What survives is "a cheap, fast dispatcher" — not "beats a frontier model". At $0.0544 per 1,000 routing decisions, routing every subtask is affordable; at $2.46 it is a line item of its own. That is the trade, and it is the reader's to make.

The frontier arm also picked a cheaper set of lanes that still passed: 56.7% saved against all-strong, against Jev's 49.4%. Two things to hold against that table. The baseline is not policy-constrained — 11 of the 60 tasks were kept local or pushed to strong by Jev's guardrail, while the LLM arm answers the raw question, so part of its agreement edge is a policy layer it never had to obey; running its lanes through the same reconciliation has not been done. And it is one set, one expert's labels, one prompt, one run each: "agreement" here means agreement with that label, not with truth. The baseline's cost was itself undercounted by ~4× at first — the provider bills thinking tokens as output while reporting only the visible answer — which flattered Jev's own number on the exact criterion the comparison is about: $0.556 per 1,000 decisions against a truth of $2.46.
