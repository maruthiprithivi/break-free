# T-023 Teach the fleet queue about CI, so a push cannot be forgotten. Modify ONLY model-gateway/src/fleet.t

## Problem
Teach the fleet queue about CI, so a push cannot be forgotten. Modify ONLY model-gateway/src/fleet.ts.

1. Extend FleetEventKind with "ci.pending" and "ci.failed".

2. A CI event needs more than the current FleetEvent fields. Add an OPTIONAL `ci` object to FleetEvent: { repo?: string; branch?: string; sha: string; runId?: number; url?: string; job?: string; deployment?: boolean }. Keep it optional so every existing event and every already-written queue line still parses.

3. Export:
   export function enqueueCi(sessionDir: string, ci: { repo?: string; branch?: string; sha: string }): FleetEvent
   which appends one ci.pending event for that sha. If a non-drained ci.pending already exists for the same sha, do NOT append a second one; return the existing event. Duplicate pending events for one sha would block twice for the same cause.

   export function resolveCi(sessionDir: string, sha: string, outcome: { state: "pending" | "success" | "failed"; runId?: number; url?: string; job?: string }): void
   - state "success": drain that sha's ci.pending by advancing the cursor past it IF it is the oldest pending event, otherwise mark it resolved in a sidecar set so pendingEvents no longer returns it. Do not rewind the cursor, and do not rewrite history in wake-queue.jsonl; the queue is append-only.
   - state "failed": append a ci.failed event carrying runId/url/job, and resolve the ci.pending the same way.
   - state "pending": do nothing.

   export function expireCi(sessionDir: string, now: number, timeoutMs: number): number
   resolves any ci.pending older than timeoutMs so it stops blocking, and returns how many it expired. A pending CI event must never be able to wedge a session forever.

4. Because the queue is append-only, resolution needs somewhere to live. Use a sidecar file <fleetDir>/resolved.json holding an array of resolved seq numbers, written 0600. pendingEvents must exclude both drained (seq <= cursor) AND resolved seqs. Keep it tolerant of a missing or corrupt file, the same way readEvents tolerates a truncated line.

5. Do not change the signature or behaviour of any existing export.

Write model-gateway/test/fleet-ci.test.mjs as a plain node:test file importing ../dist/fleet.js against a temp dir, covering: enqueueCi twice for the same sha yields one pending event; resolveCi success removes it from pendingEvents; resolveCi failed removes the pending one and adds a blocking ci.failed carrying the url; resolveCi pending is a no-op; expireCi clears a stale pending and returns 1; a resolved event stays resolved across a fresh read (simulated restart).

## Acceptance criteria
fleet.ts exports enqueueCi, resolveCi and expireCi with those exact semantics, FleetEvent gains an optional ci object, and the sidecar resolved.json is honoured by pendingEvents. No existing export changed signature. test/fleet-ci.test.mjs covers all six cases. The supervisor must reject any round where an existing export was altered or where the queue file is rewritten in place rather than appended to.

2. **Changes**

- `model-gateway/src/fleet.ts`
  - `FleetEventKind` now includes `"ci.pending"` and `"ci.failed"` (line 14).
  - Added exported `FleetCi` interface and optional `ci?: FleetCi` on `FleetEvent` (lines 16–33), so old queue lines still parse.
  - Added `RESOLVED_FILE = "resolved.json"` (line 44).
  - Added tolerant `readResolvedSeqs` / `writeResolvedSeqs` / `markResolved` / `pendingEventsInDir` helpers (lines 161–190). Missing/corrupt `resolved.json` is treated as empty; writes use mode `0600`.
  - `pendingEvents` now delegates to `pendingEventsInDir`, filtering out both drained (`seq <= cursor`) and resolved seqs (lines 238–241).
  - Added `enqueueCi` (lines 267–276): dedupes non-drained `ci.pending` by sha and otherwise appends one.
  - Added `resolveCi` (lines 278–312): `"pending"` is a no-op; `"success"` drains via cursor only when the event is the oldest pending, otherwise marks it resolved; `"failed"` resolves the pending the same way and appends `ci.failed` with `runId`/`url`/`job`.
  - Added `expireCi` (lines 314–328): resolves stale `ci.pending` events and returns the count.

4. **Open questions / risks**
- `enqueueCi` dedupes against any non-drained (`seq > cursor`) `ci.pending`, including one that has been resolved via the sidecar. This matches the literal “non-drained” wording, but it means the same sha will not be re-enqueued until the cursor passes the old event. If the intent is to allow re-enqueue immediately after sidecar resolution, `findNonDrainedCiPending` should also exclude resolved seqs.
- `resolveCi` with `state: "failed"` appends a `ci.failed` even when no `ci.pending` exists for that sha, per the spec’s unconditional wording. If repeated status polls call `resolveCi` for the same failed sha, duplicate `ci.failed` events are possible (the same is true of the existing append-only queue in general).
- The new test imports `../dist/fleet.js`, so it requires the normal `npm run build` before `node --test`.

Review: revise — The fleet.ts changes implement the CI queue semantics and sidecar handling correctly in an append-only way, and the new test file covers the required cases. However, the working tree also contains large, unrelated changes to videos/src/script.json that violate the explicit 'Modify ONLY model-gateway/src/fleet.ts' instruction and must be reverted before this can land.
