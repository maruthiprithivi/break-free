# T-024 Make pushes enqueue CI work and make the watcher resolve it.

## Problem
Make pushes enqueue CI work and make the watcher resolve it.

1. In model-gateway/src/workspace.ts, after a successful `git_push`, call enqueueCi with the current sha (git rev-parse HEAD) and branch. In model-gateway/src/github.ts, after a successful `gh_merge_pr`, do the same for the merge commit if it is available. Both must be best-effort: a failure to enqueue must never fail the push or the merge, so wrap in try/catch and carry on.

2. In model-gateway/src/index.ts, inside the fleetCheck() path, before computing `blocking`:
   - call expireCi with config.fleet.ciTimeoutMs (add that setting to config.ts with a default of 20 minutes; follow the existing config style)
   - for each remaining ci.pending, shell out via the same mechanism github.ts uses to run `gh run list --json databaseId,status,conclusion,url,headSha,name --limit 20` for the repo, find the run whose headSha matches, and call resolveCi with success/failed/pending accordingly. A workflow that is queued or in_progress stays pending.
   - if the repo has deployments for that sha, a successful workflow is NOT enough: check `gh api repos/{owner}/{repo}/deployments?sha=<sha>` and the latest status of each, and keep the event pending until the deployment reports success, failing it on error/failure. A green workflow is not a healthy deploy.
   - if `gh` is missing or unauthenticated, skip all of this silently and behave exactly as today.

3. In the --hook output, when a ci.failed event is pending, the reason must name it and carry the run URL, for example: `CI FAILED on abc1234 (build) - https://github.com/o/r/actions/runs/123 - fix it before ending the turn`. When only ci.pending remains: `CI pending on abc1234 - waiting on the run you caused`.

4. All of this must keep --fleet-check exiting 0 always and writing nothing to stderr in --hook mode.

Do not change any unrelated tool.

## Acceptance criteria
git_push and gh_merge_pr enqueue a ci.pending best-effort and never fail because of it. fleetCheck expires stale pending events, resolves the rest from gh, treats deployment status as separate from workflow status, and degrades silently when gh is unavailable. The hook reason names a CI failure with its URL. --fleet-check still always exits 0 with clean stderr. config.fleet.ciTimeoutMs exists with a 20 minute default.
