## Problem
Build the A/B harness that issue #22 needs. The issue says criteria 2, 3, 8 and 11 are unmeasured because nothing has ever run the crew twice on the same commit and compared real verify outcomes. The infrastructure to COLLECT the data exists; what is missing is the thing that RUNS both arms and reports the table.

If you run low on rounds, finish what you have, make it compile, and list the rest under 'Open questions'. Read ONLY these, and stop when you can act:
1. model-gateway/src/bench.ts — the existing `bf bench route` command, its output shape and how it reports `measured`
2. model-gateway/src/routing.ts and model-gateway/src/jev.ts — lanes, confidence, threshold
3. model-gateway/src/ledger.ts — grep for `scorecards` and read that function and the record type
4. model-gateway/src/index.ts — how CLI branches are added in main() (look for `--selftest`, `--bench`, `--fleet-check`) and how run_plan is registered
5. model-gateway/bench/demo-plan.json — the plan shape

BUILD: a new CLI command in the existing style that takes a plan file and runs it TWICE on the current commit — arm A with the configured routing engine, arm B with every task pinned to the `strong` alias — keeping each task's `verify` command identical between arms, then reads the resulting scorecard lines and prints the comparison.

It must report, from real data and never from worker prose:
- first-pass verify pass rate per arm, and the delta (criterion 2: routed must be within 5 points of all-strong)
- pass rate after one retry per arm (criterion 3)
- calibration buckets: tasks at confidence >= 0.8 versus < 0.5, and the verify failure rate of each (criterion 8 wants the high-confidence bucket failing at most half as often)
- actual spend per arm from cost_report routing_savings

HARD REQUIREMENTS:
- Pass rates come from the scorecard `verify_ok` field, which is the gateway's own exit code. Never from a model's report text. Say so in a comment.
- A criterion that misses its target must be printed as a MISS, not smoothed over. A harness that can only report success is worthless.
- If a plan has no `verify` command on a task, that task cannot contribute to criteria 2 or 3. Exclude it and say how many were excluded, rather than silently counting it as a pass.
- Handle the empty case: no scorecards, or one arm produced none, must print what is missing rather than dividing by zero.
- Add a test in model-gateway/test/ in the style of the existing tests, driving the computation over FIXTURE scorecard rows. Do not make the test run real models or real plans — it must be offline and deterministic. Test at least: the pass-rate maths, the exclusion of unverified tasks, the calibration bucketing, and the empty case.

Do not run npm or any build — there are no node_modules in this checkout and you do not have the `run` capability. Write code that compiles under the existing TypeScript settings; match the surrounding style exactly, including the file-header comment convention explaining why the file exists.
