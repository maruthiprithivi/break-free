## Problem
Write the integration design for issue #31: break-free wrapping firstmate. Output ONE new file, docs/firstmate-integration.md. Change nothing else except a changelog fragment.

BUDGET RULE, read this first: you have 30 tool-call rounds. Spend AT MOST 15 reading. From round 16 onward, WRITE THE FILE. Two previous workers on this exact question burned every round reading and returned empty reports — that is the failure mode to avoid. A short design grounded in six files beats no design after reading twenty. Write the file early and improve it if rounds remain.

THE DECISION THAT FRAMES EVERYTHING, from the repository owner: where firstmate already provides something, break-free USES it and does not rebuild it. Do not propose reimplementing anything firstmate has.

VERIFIED FACTS. Treat these as established; do not spend rounds re-deriving them:
- firstmate is an agent distro: a cloned repo of AGENTS.md, skills and ~410 bash scripts that a harness follows. Not a CLI, not an MCP server, not a model. It is third-party (github.com/kunchenguid/firstmate) and must never be forked.
- firstmate OWNS, and break-free must drop its own versions of: worktree lifecycle (bin/fm-spawn.sh via treehouse, pool slots, project lock), crew spawning into terminals (five backends: tmux/Herdr/cmux/zellij/Orca), fleet supervision and the watcher (bin/fm-watch-arm.sh), fleet sync and branch pruning (bin/fm-fleet-sync.sh), merge authority (bin/fm-merge-authority-lib.sh).
- firstmate does NOT provide, so break-free keeps: model routing, tiers and the tier floor, the per-provider circuit breaker, gateway-run verification, cross-vendor review, and CI run watching (checked: bin/fm-lint-workflows.sh is actionlint, not Actions run watching; no Actions watcher exists upstream).
- firstmate does NOT predict merge conflicts or order merges. bin/fm-merge-local.sh:111-115 is fast-forward only and REFUSES a diverged branch, telling the human to rebase by hand. bin/fm-fleet-sync.sh never compares two branches.
- break-free ALREADY has model-gateway/src/worktrees.ts with a registry at <repo>/.git/break-free/worktrees.json and a conflicts() method — but conflicts() only INTERSECTS CHANGED FILE PATHS, so it reports an overlap whenever two branches touch a file in common, even when the merge is clean. Read that file; it is the hinge of the design.
- git merge-tree --write-tree <a> <b> performs a real three-way merge in memory, no worktree, no checkout. Measured on this repository: 15 branch pairs in 1 second on git 2.50.1.
- bin/fm-fleet-sync.sh:228-231 documents that PRs in this fleet are squash-merged, so a merged branch is NEVER an ancestor of the default branch. Ancestry cannot prove 'landed'. Any design that uses ancestry to decide what is merged is wrong.
- bin/fm-update.sh fast-forwards from origin, FAST-FORWARD ONLY, never force or stash, never touches data/ state/ config/ projects/. It emits a parseable summary with 'reread-firstmate: yes|no'. It takes NO arguments and its base is hardcoded to origin, so it cannot express a pin.

Read ONLY these to ground the design: model-gateway/src/worktrees.ts (essential), model-gateway/src/index.ts (only to see how MCP tools are registered and how CLI flags branch in main()), .firstmate/bin/fm-merge-local.sh, .firstmate/bin/fm-update.sh.

The document must contain, in this order:

1. **Ownership**, as a table: capability | owner after integration | the artifact that implements it. Use the verified facts above. Include the rows break-free drops and state what happens to the code it drops (delete, deprecate, or keep behind a flag) — name the file.

2. **Where the distro lives and how it updates.** One managed location, not per-repo. The supply-chain gate is the point: upstream pushing to its default branch would otherwise become the instructions the user's agent obeys, unreviewed. Specify pinning to a commit sha, how a human is shown what changed before it goes live, and rollback. Say what must never be auto-applied. break-free decides WHICH commit; upstream's own fm-update.sh moves the tree.

3. **Merge coordination**, the reason the issue exists. Five worktrees finish at different times and merging them back conflicts with no visibility. Design:
   a. the upgrade of worktrees.ts conflicts() from path intersection to a real merge-tree probe, naming the function you would change and what it returns
   b. a merge ORDER rule, justified
   c. blast radius per merge — check whether model-gateway/src/codemap.ts exists and use it if it does
   d. the user-facing surface: the MCP tool or CLI output, sketched for five in-flight worktrees

4. **Collisions still open**, as a short list of decisions with a recommendation each: the duplicate turn-end Stop hook (break-free appends to the hooks.Stop ARRAY in setup.mjs around line 1148, so both hooks run and both vote on whether a turn may end); two project-mode vocabularies (firstmate no-mistakes/direct-PR/local-only+yolo vs break-free guarded/pr-only/local-only+mergeAutonomy); two task boards (firstmate fm-backlog-* in FM_HOME vs break-free .break-free/ ledger).

5. **What is not decided**, honestly listed.

Ground claims in file paths. Where you did not verify something, say so in the document rather than asserting it.
