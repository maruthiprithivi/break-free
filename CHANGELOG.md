## 4.2.1 — 2026-09-21

- **A nested session no longer picks a harness by coin flip (#68).** An outer harness's environment is inherited by everything it spawns, so a Codex session started from inside Claude Code carries both marker sets — and `bf firstmate` resolved that tie by the order names happened to appear in a list. Two claimants is now treated as no answer: the choice falls through to `firstmate.harness` or what your install wired, which you actually chose, and the command says so rather than deciding quietly. A single claimant is still trusted.

## 4.2.0 — 2026-09-21

- **The firstmate provisioning path is now tested, and a failed clone no longer reddens the install (#65).** Cloning, pinning and writing the standing rule had no coverage at all: the installer self-test pinned firstmate off because a CI container cannot reach GitHub, so that code had run exactly once, by hand. `BREAK_FREE_FIRSTMATE_ORIGIN` lets the origin be a local repository, and the self-test now provisions from one and asserts all three outcomes — the clone, the pin in the config, and the rule in `~/.claude/CLAUDE.md`. A clone that fails is a WARN rather than a FAIL: break-free works without firstmate, and turning a break-free install red because GitHub was unreachable blames the wrong thing. The standing rule also follows a project-scope install, since a clone nothing points at is a clone nothing uses.
- **`bf firstmate` starts the harness you are actually using (#66).** It took the first verified harness on PATH, and `claude` is first in that list — so typing `bf firstmate` inside a Codex session on a machine with both installed handed back Claude. The session you are in now wins: `CODEX_SESSION_ID`, `CLAUDECODE`, `CURSOR_AGENT`, `GROK_AGENT`, `PI_CODING_AGENT` and `OMP_EXT` identify the running harness, taken from what each one actually sets rather than guessed. After that come `firstmate.harness` if you stated one, then the harnesses your install actually wired (from `last-install.json`), and only then the shipped order. An explicit `--harness` still wins outright even when that harness is not installed, so the refusal says "not on PATH" instead of quietly handing you something else, and a signal pointing at something uninstalled steps aside rather than blocking the fallback.

## 4.1.0 — 2026-09-21

- **firstmate ships with break-free, and any session knows it is there (#31).** The installer provisions it by default, pulls the latest on every install and update — through upstream's own fast-forward-only `fm-update.sh`, never a reimplementation — and re-pins to what landed. A standing rule goes into `~/.claude/CLAUDE.md` and `~/.codex/AGENTS.md` beside the delegation rule, so an ordinary session started anywhere already knows the distro exists and when to engage it. That is the mechanism that matters: a harness reads `AGENTS.md` from where it starts, so a session started in your project would otherwise never see a distro living somewhere else. The rule costs about 350 tokens; firstmate's own 82K of instructions are read only when a job actually wants a crew, so a session that never spawns one pays nothing for it. `--doctor` reports whether an upstream update is waiting and whether it changes the instruction surfaces, and never takes it on its own. `bf firstmate` still starts a dedicated firstmate-led session, but you no longer need it to use the distro.

## 4.0.1 — 2026-09-20

- **`bf firstmate` looks up a harness on PATH without a shell.** It ran `command -v <bin>` through `/bin/sh`, which concatenates rather than escapes its arguments — node deprecates that for the reason that applies here: the binary name comes from `--harness`, so it is caller input. It now walks `PATH` and checks for an executable directly, and refuses a name containing a path separator outright.

## 4.0.0 — 2026-09-20

- **`bf firstmate` starts a firstmate-led session, and the installer can provision the distro (#31).** This is the honest shape of "break-free uses firstmate": an MCP server cannot make an already-running client adopt firstmate's identity, because the distro is instructions a harness reads at startup and startup is over — so break-free launches a new session inside the distro instead, and firstmate leads it. The session announces itself as `break-free -firstmate` before it takes the terminal. It refuses to launch when the distro is drifted or dirty, which would run instructions nobody approved, and refuses a harness firstmate has not verified as a primary, because its turn-end guard and watcher re-arm are per-harness and an unsupported one would look like it works while the supervision it depends on is silently absent. `FM_HOME` is kept outside the code root so rolling the code back never hides the crew registry or the backlog. The installer asks once, defaults to no, clones with full history (pinning and reviewing an update both need to diff revisions) and pins to the commit it landed on.
- **break-free can provision and audit the firstmate distro (#31, first slice).** `firstmate_status` reports where the distro lives, the commit on disk, the pinned commit, and which of five states the pin is in — `clean`, `drifted`, `dirty`, `unpinned` or `unknown`. A dirty tree at the approved commit is not a clean pin, because the bytes on disk are what an agent reads; an unreadable checkout reports `unknown` rather than fine. `firstmate_update_plan` shows what a revision would change in the surfaces that steer an agent — including executable harness assets like `.claude/settings.json` and `.cursor/hooks.json`, which run without anybody reading them — alongside the full changed-file list, and it never moves the checkout. The tree is only ever moved by upstream's own fast-forward-only `fm-update.sh`, returned with the caveat that it aims at origin rather than the revision you reviewed. Off by default: firstmate becomes the lead of the sessions it runs, which is the user's call to make.
- **The fixed context cost is down 61%, from 17,376 estimated tokens per session to 6,787 (#47).** A tool's schema is sent to the lead in every session and re-sent every turn whether or not anything calls it, and 55 schemas were the single largest standing cost in the product. Under the new default `context.toolProfile: "compact"`, break-free advertises execution and its lifecycle — `delegate`, `run_plan`, `supervise`, `review`, the `job_*` tools, `ledger_resume`, `list_models` — and moves the other 45 behind `bf_discover` and `bf_invoke`. **Nothing becomes unreachable**, which is what separates this from simply not registering a tool: `bf_discover` lists the operations and returns any one's full schema, and `bf_invoke` runs it through the same zod validation an advertised tool would use, so an invalid call fails identically rather than reaching the handler. Execution keeps its lifecycle on purpose — advertising `delegate` while hiding `job_cancel` would leave an agent able to start work it has no typed way to stop. Set `toolProfile: "full"` to advertise everything as before.
- **A crew session in one project no longer blocks the turn-end guard in another (#51).** #43 gave events a workspace, but they were stamped with the workspace of the gateway that *observed* them. That is right for a job, which the gateway started, and wrong for a harness session, which has its own `cwd` — so a Codex agent working in one worktree blocked turns everywhere else, and could not be drained, because every check classified a fresh `harness.output` as its pane kept changing. The snapshot now carries each session's directory, `classify` stamps harness events with it, only `job.*` events take the gateway's workspace, and the running-harness count is scoped to this workspace. A session with no recorded directory stays unowned and visible to everyone rather than being adopted by whoever noticed it.
- **The context report was under-reporting by 79%, and now measures what the client actually receives (#54).** The tool-schema estimator counted field names and their descriptions only, omitting types, enums, nested objects and required lists — so a tool's real serialized JSON Schema was far larger than the number reported. Schemas are now serialized with `zod-to-json-schema`, the same library the MCP SDK uses to answer `tools/list`. The fixed session cost is 17,005 estimated tokens, not 10,139, and the ranking changed with it: `run_plan` is the heaviest tool at 1,694 rather than the 421 the proxy showed, because its nested task-array schema dominates. The prose cuts in 3.9.0 were real, but the percentage reported against them was measured on a proxy and overstated.

## 3.9.0 — 2026-09-20

- **What break-free costs a session is now measured (#47).** `context_report`, and `--doctor`, account every surface the gateway adds to the lead's context — tool schemas, server instructions, the ledger resume brief — against `context.budgetTokens` (default 7500, matching firstmate's startup-memory allowance so anyone running both holds one number). The estimator is `ceil(UTF-8 bytes / 3)`: deliberately crude, stable across providers, and rounding up so a budget never flatters itself. Only surfaces paid in every session are held to the budget, since an on-demand cost is a choice the caller made, and the largest unavoidable contributor is named because that is where an argument should start. The first run corrected a hand count: 53 tools, not 47, and 11,517 tokens per session against a 7,500 budget.
- **The fixed context cost is down 12%, from prose alone (#47 phase 2).** Break Free charged every session 11,517 estimated tokens before any work happened; it now charges 10,139. The server instructions lost 65% (883 to 313) by dropping a vendor roll-call and a mode-by-mode catalogue that the tool schemas already state. `CapabilitySchema` — charged once per tool that uses it, five times over — kept every limit that matters (the workspace jail, never protected branches, never force, `github` implies `git`, `run` is allow-listed only) and lost the parentheticals. `delegate` went from 1,169 to 794 and `supervise` from 757 to 603, keeping the sentences that change behaviour: give capabilities deliberately, the supervisor should be a different vendor, and the gateway runs `verify` itself so a worker cannot fake it. No tool was removed and no capability was lost.

## 3.8.0 — 2026-09-20

- **Routing can be measured against all-strong on real runs (#22).** `bf ab <plan>` runs the same plan twice on one commit — once through the configured routing engine, once with every task pinned to `strong` — keeping each task's `verify` command identical, then reports first-pass and post-retry verify rates per arm, the calibration buckets (confidence >= 0.8 versus < 0.5) and the actual spend of each arm. Pass and fail come from the scorecard's `verify_ok`, which is the gateway's own exit code, so no worker can narrate its way to a pass. A criterion that misses its target prints as `MISS`, tasks with no `verify` command are excluded from the rates and counted, and an arm that produced nothing reports `NOT MEASURED` rather than a number.
- **Changelog entries are one file per change.** Every branch used to append to the same `Unreleased` block, so every pair of branches conflicted there on a line neither author cared about — in this repository it was the single largest source of merge conflicts, present in every conflicting pair of open branches. Entries now live in `changelog.d/<issue>-<slug>.md`, and `scripts/changelog.sh release <version>` folds them into `CHANGELOG.md` at release time.
- **Design: break-free wraps firstmate instead of competing with it (#31).** `docs/firstmate-integration.md` records the ownership split (firstmate owns worktree lifecycle, crew spawning, fleet supervision and merge authority; break-free keeps routing, the tier floor, the circuit breaker, verification, cross-vendor review and CI run watching, and adds the merge-conflict forecast nobody has), the pinning/rollback design that keeps an upstream push to firstmate's default branch from becoming the instructions the user's agent obeys (break-free decides *which* commit through a bare mirror; upstream's own unmodified `fm-update.sh` moves the tree), and the one join gap the issue was opened for: `WorktreeRegistry.conflicts()` in `model-gateway/src/worktrees.ts:250-265` only intersects changed paths, so the design upgrades it to a real `git merge-tree --write-tree` probe plus a merge order and per-merge blast radius. No source file changed; the open collisions (two turn-end Stop hooks, two project-mode vocabularies, two task boards) and everything still undecided are listed in the document.
- **A squash-merged worktree is finally recognised as merged (#34).** The registry decided a branch had landed by ancestry (`rev-list --count base..HEAD`), which is never zero for a squash merge: the branch's own commits are replayed as one new commit and never enter the base. Those worktrees sat at `active` indefinitely and kept contributing their changed paths to every overlap forecast, so the longer a repository used squash merges the more of the forecast was noise. Merged is now decided by content — if merging the branch would produce base's own tree, it has landed — which catches squash and rebase merges as well as ancestry, in one in-memory three-way merge with no checkout. The recorded `reason` says which test decided it, because they fail differently and a wrong `merged` is worse than a stale `active`.
- **An empty agent config no longer fails the install (#36).** A zero-byte config file was treated as unparseable and reported as `is not valid JSON — fix it by hand first`, turning an otherwise clean install RED and asking the user to hand-edit a file whose entire content is nothing. Refusing to overwrite a file that cannot be parsed is right when it holds real content — clobbering someone's MCP registrations is far worse than a failed step — but zero bytes hold nothing to lose, so they are now read as `{}`. The fix is in `readJsonSafe`, so it covers every agent config at once, including `~/.claude/settings.json`: an empty one previously took the turn-end guard down with it.
- **`read_file` no longer overstates every file by one line (#38).** A trailing newline terminates the last line rather than beginning an empty one, but the tool counted the raw `split("\n")`, so a three-line file was reported as `lines 1-4 of 4` with a phantom numbered blank line at the end. Every delegated worker reads code through this tool, so line numbers cited back to the lead were wrong at the tail of nearly every file. `search` split the same way, where a pattern like `^$` could report a match on a line that does not exist. A file that genuinely ends in a blank line still reports that line, and a file with no trailing newline is unaffected.
- **A real code graph is used when you have one (#41 phase 2).** `knowledge.graph.provider` chooses which graph answers structural questions: `auto` (default) prefers a detected code-graph MCP server and falls back to the builtin regex import map, `builtin` pins the map, and an explicit server name uses that one. Detection is by the shape of a server's tools rather than its name — two matches from `search_graph`, `trace_path`, `query_graph`, `get_architecture`, `get_code_snippet`, `index_repository` — because a name is not a contract and one lone search tool cannot answer a structural question. A named provider that is not available is an error rather than a quiet fall back to regex import edges, which nothing in an answer would reveal. `--doctor` reports the configured value, what it resolved to, and why.
- **The ledger can live in your Obsidian vault (#41).** `obsidian_link` surfaces a project's ledger inside a vault: `link` (default) symlinks it into `<vault>/break-free/<project>` so a note edited in Obsidian is the same bytes git sees, `index` writes a single note pointing at it, and `off` does nothing. Detection reads Obsidian's own vault registry rather than scanning the filesystem, so it is exact and cannot wander; a machine without Obsidian stays silent rather than warning about not having it. It never copies, and it refuses rather than overwrites — anything at the target that is not our own link to that same ledger is left untouched, because a vault is someone's notes. `--doctor` now reports the detected vault and the configured graph provider.
- **A finished job in one repository no longer blocks a turn in another (#43).** The fleet wake queue and its cursor live in the shared session directory, and the cursor was a single integer, so one machine-wide position had to serve every workspace: a `run_plan` that completed in one project left a pending event that blocked the turn-end guard in an unrelated one, clearable only by draining a result nobody had read. Events now carry the workspace that produced them, `--fleet-check` and `fleet_status` filter to the current workspace, and the cursor is a per-workspace map. A cursor file still holding a bare integer is read as a baseline that applies to every workspace, so upgrading re-emits nothing, and rows written before the change belong to nobody and stay visible to everyone rather than stranding an event no session will own. The hook now names what is pending (`job.done run_plan-…`) instead of only counting it.

## 3.7.0 — 2026-09-19

- **Stall detection: liveness measured in tool calls, not wall-clock (#12 Phase 2).** A worker that spins for half an hour without writing a byte was the failure this issue was opened for, and nothing detected it. `src/agent.ts` now tracks `lastToolCallAt`, the tool calls and the files written per task. `workers.stallWarnMs` (default 3 min) emits a repeating progress line and a runtime log entry; `workers.stallAbortMs` (default 10 min) aborts; `workers.stallWarnIterations` (default 4) warns when a write-capable worker has written nothing. `0` disables each. The watchdog is armed for the time **left since the last activity**, so a long-running command earns no extra window and a worker that keeps calling tools is never stalled for taking a long time overall. An abort raises a distinct `StalledError`, so the task dies as `stalled` and never as `failed`: `run_plan` rows carry `stall: {ms_since_tool_call, tool_calls, files_written}`, the report prints `STALLED`, the journal writes `STALLED:`, `delegate` surfaces `ERROR: stalled: …`, and `delegate`/`supervise`/each `run_plan` task take `stall_abort_ms`/`stall_warn_ms` for the per-task escape hatch. Ledger status stays `blocked` rather than gaining a `stalled` value — `TASK_STATUSES` has no member for it and the ledger line names the stall.
- **Hand over a brief, not a transcript (#12 Phase 3).** A substitution now checkpoints the **task** — instruction, acceptance criteria, files touched so far (from the same tree snapshot the policy review uses, minus `.break-free` bookkeeping) and the last gateway verification — and rebuilds a compact brief capped to the target model's window (`providers.<name>.contextTokens`, 8192 default), using half the window because the worker still needs room for its own turns. The header and file list are mandatory, the rest is cut to fit, and a final hard cap means it can never exceed the window. **A design point that only appeared in testing:** the router picks the candidate inside the call, so a brief built after the substitution is discovered would only reach a substitute that came back for a second turn — the hung substitute that never calls a tool would never see one. The brief is therefore prepared before the first request and handed to every candidate except the intended one, and the test asserts it is what the substitute's **first** request contains. Handovers land in `meta.handovers`, the journal (`handover A -> B (auth) · 1 file(s) touched · brief 200/400 tokens (truncated)`) and the `run_plan` task entry.
- **Fix (#25): `bf validate --with-routing` routed nothing and reported success anyway.** The spawned server was given the user config, whose `routing.engine` defaults to `off`, so every route call answered `engine: "off"`, the routed arm ran **zero workers**, was reported as errored rows — and the command exited 0. The engine now travels on the `route` call (the same session-level override `run_plan` uses) and the dead config file written with `{}` is gone. Three reporting defects went with it: the header counts only runs that produced a verify result, a never-run row names its real cause (no decision, or escalated below `routing.threshold` with the confidence) instead of blaming lane mapping, and an arm with no verify result exits non-zero.
- **Criteria 2, 3 and 8 are measurable now.** `TaskOutcome` keeps `confidence`, `lane` and `attempts`; a failed verify is retried once (`--attempts`) with the failed command and exit code handed to the worker, so first-pass and after-one-retry are both visible; and the report treats a band with no runs as **unmeasurable** rather than as 0% failures — `criteria.calibration.holds` is `null`, not `false`, so no consumer can quote a verdict out of an empty bucket. Measured on the 10-task crew set with routing on: first-pass 100% on both arms (a ceiling, not a margin — the routed arm is 8 runs because two tasks were escalated below threshold), and criterion 8 is unmeasurable by construction because the sub-0.5 band is exactly what the threshold escalates away.
- **Fix (#26): an unpriced model was reported as $0, which inflates routing savings.** `priceFor` returns `{0,0,priced:false}` for a model with no table entry, so the call was costed at zero and `routing_savings` — actual spend against the same usage replayed at `strong` — printed a saving inflated by a **table gap** rather than by a real saving. `deepseek/deepseek-flash` now has a rate ($0.30 in / $1.20 out per Mtok, from the DeepSeek pricing page, using peak cache-miss rates because understating is a wrong number rather than caution). `cost_report` names every unpriced call and marks affected totals as lower bounds, and **`routing_savings` refuses the number outright** when anything in the window is unpriced rather than printing an inflated one. A declared zero still counts as priced, so a genuinely free local endpoint keeps a working savings line. The bench is untouched: it prices through the shipped tables and no alias resolves to the new entry.
- **Fix (#13): a local endpoint can be configured without hand-editing config.** `configure_provider` had no `requires_key` argument, so a keyless local server could only be completed by editing the config file by hand — a parameter that did not exist was silently ignored. It now takes `requires_key`, defaulting to false only on the call that **defines** a loopback/private base URL (`isLocalEndpoint` covers loopback, RFC1918, CGNAT/tailnet ranges and single-label hosts; a public FQDN never counts, and an unparseable URL is not treated as local). The default is deliberately narrow so an unrelated update cannot flip a provider's auth, an explicit key or `requires_key` always wins, and the project scope still refuses it. `list_providers` reports `requires_key` and, for a private endpoint still asking for a key, prints the one-call fix; `test_provider` explains an empty reply instead of leaving it unexplained.

## 3.6.0 — 2026-09-19
- Videos rebuilt: an intro plus six walkthroughs (delegate a model, hand off to another harness, split a job in parallel, get an independent verdict, nothing gets left behind, resume across sessions). The scripts are claim-sourced against the code in `videos/CLAIMS.md`; the earlier set described a product that did not exist. The scene changes on every narration beat rather than a still drifting behind static panels, captions occupy a reserved band no stage content can enter, and every video opens and closes on a card.
- **A per-provider circuit breaker, so a wedged host costs one timeout instead of one per call.** A host that accepts TCP and then goes silent looks healthy: the request sits until `timeoutMs`, and with `retriesPerCandidate` it does that twice. Two consecutive timeout/network failures now open that provider's circuit; its candidates are skipped instantly with reason `circuit_open`, the chain continues to the next candidate, and a `provider.circuit_open` event goes on the fleet queue. Only host-level symptoms count as strikes. After `fallback.breaker.cooldownMs` the next call is a trial — strikes are not forgiven, so one further failure re-opens it and only a real answer clears it. State is persisted, so a restart does not re-learn the same dead host, and `--doctor` reports `open_circuits`.
- **A tier floor, so fallback never quietly gets weaker.** Every model carries a tier (3 frontier, 2 solid, 1 small/local) from `DEFAULT_TIERS`, overridable per provider or per `provider/model` in `tiers`. The floor for a call is the tier of the model actually asked for, so a tier 3 request is never answered by tier 1 behind the caller's back. `delegate`, `supervise` and each `run_plan` task take `min_tier` and `allow_downgrade`; globally there are `fallback.minTier` and `fallback.allowDowngrade`. When every candidate above the floor fails, the error names what was held back rather than reading like a provider outage. A downgrade that does happen is reported — `meta` carries `requested_model`, `tier` and `downgraded`, and `run_plan` prints `route: strong -> ollama/qwen3-coder:30b (auth) [tier 3 -> 1]` — while a same-tier fallback stays quiet.

## 3.5.0 — 2026-09-19

- **Fix: the suite failed under the runner's own file parallelism, not under CPU load.** `test/gateway.test.mjs` set `defaults.timeoutMs: 1500`, and config precedence makes that the client deadline for *every* mock call, so a loopback round trip under contention failed a test on a timeout unrelated to what it asserted. Two attempts to reproduce with pure CPU load failed (8 and 10 `yes` hogs, 46/46 green); running **8 concurrent instances of the file** — what the default runner does across a 10-core box — produced **4 of 8 red runs at load ~49**, and the same setup with the fix produced **8/8 green and zero timeouts**. The fixture default is now 8000 ms, and the one test that deliberately exercises the timeout path takes its 1500 ms deadline from a provider entry (`mockshort`) so the override stays load-bearing — a negative control with that deadline forced to 20 s makes the test fail, i.e. the timeout path cannot silently stop being exercised.
- **Fix: a test that could not pass on its own.** `review returns a parsed JSON verdict...` asks for `use_git_diff: "HEAD~1"` while the fixture makes exactly one commit, so it only worked because an earlier test happened to commit a second revision — running it alone failed with `SyntaxError: Unexpected token 'E', "ERROR: git"...`, and when that earlier test flaked this one failed with it (the 197/199 pattern). It now commits its own second revision and asserts the diff names the file it committed.
- **Fix (#16): a verify failure now says where it ran.** The issue's stated cause was wrong, and measuring it was the fix's first step: `verify` already ran at the workspace root, not the gateway's cwd (probe: a script present only in the gateway's cwd fails with `Cannot find module '<ws>/…'`). The real defect was that neither the report nor the metadata named the directory, so a command written for a monorepo subdirectory read as a broken suite. `CommandResult.cwd` is now a required field set by `runCommand` and surfaced everywhere it matters: the verification header (`… FAILED (exit 3, 37 ms) in /path/to/ws`), `VerifyMeta.cwd`, the ledger outcome line, the worker's own `run_command` header, and the ENOENT diagnostic (`command not found: X; cwd /path`).
- **Fix (#17): re-running a plan reuses its ledger task instead of minting duplicates.** Ledger tasks created by `run_plan` now carry plan identity (`plan` and `plan_task` frontmatter), so a second run resolves the existing task by (goal, task id) rather than creating `T-0NN` again, updates a stale `verify` command, and closes a reused `blocked` entry at `done` with a pointer to what closed it. Identity is the task id, not the title, so the same id in a different plan stays a separate task. The historical duplicates that predate the identity fields are not migrated — they cannot be linked, and reconciling them needs a data migration.
- **The landing page now shows what the project is.** `docs/index.html` mentioned neither routing nor Jev; it now covers the three engines, a routed plan's shape and provenance, the tripwire (with its 4% false-flag rate on 175 real merged diffs), and — as its own section — **the comparison the project loses**: against a frontier LLM prompted as a router, Jev is 47.7× faster and 45.1× cheaper per decision but 23.3 points behind on agreement. Every number is traceable to a line in `docs/routing.md` or `docs/tripwire.md`, and no claim contradicts a measurement.
- **`bench/validate-crew.jsonl`** — ten tasks whose two arms are on *different* lanes (`strong` vs `fast`), for `bf validate`: 20 real runs, both arms 10/10, the cheap arm ~2.3× faster per task (9.4 s vs 21.6 s mean). See #22 for what a ten-task fixture on a synthetic project cannot establish.
- **Routing: something else picks the model.**
- **The frontier-LLM-as-router baseline is real now, and it says Jev loses on judgement.** The `llm` arm of `bf bench route` was a hardcoded stub that always reported "unmeasured — needs a provider key"; nothing was ever implemented behind it. It is now opt-in (`--llm [provider/model]`), gives the baseline the **same lane definitions Jev gets** (`LANE_SPEC` verbatim) and the same task facts, batches 12 tasks per call exactly as the `ms/plan` column assumes, and prices its calls from the usage the API reports. **Measured live, 60 tasks, `gemini-3.1-pro-preview`: exact lane 95% vs Jev's 71.67%, crew lanes 93.88% vs 83.67%, 15,517 ms/plan vs 326 ms, $2.4556 vs $0.0544 per 1,000 decisions.** So criterion 11 **fails on two of its three clauses** — Jev is 47.7× faster ✓ but only 45.1× cheaper ✗ and 23.3 points behind on agreement ✗. The honest claim is "Jev is a cheap, fast dispatcher", not "Jev out-thinks a frontier model"; `docs/routing.md` says so, with the caveat that the baseline is not policy-constrained while Jev's lane is (18.33% forced).
- **Google Gemini is a provider.** `gemini`, over its OpenAI-compatibility layer, verified live: tools work, and the model list was read from the API rather than guessed — the `gemini-2.5-*` ids are retired for new accounts (404), and the pro/`-latest` tiers are reasoning models. Published rates are in the price table (Pro $2/$12 per Mtok, 3.5 Flash $1.50/$9), so the cost column for the baseline is priced rather than assumed.
- **Fix: a reasoning model's hidden thinking tokens were billed as zero.** Google's shim reports only the visible answer in `completion_tokens` while charging thinking as output — one real request returned `completion_tokens: 2, total_tokens: 600` for a two-token reply. Costing the baseline that way charged it **$0.556 per 1,000 decisions when the truth was $2.46**, flattering break-free's own router in the exact comparison criterion 11 is about. `costUsd` now bills output as `max(completion_tokens, total_tokens - prompt_tokens)` and the arm reports how many were thinking.
- **Fix: `bf validate --help` ran a real validation, and could reset a repository.** `--help` was handled only at the top level and unknown flags were silently ignored, so `bf validate --help` executed the command with its defaults — the shipped 60-task set, `--workspace` defaulting to the current directory — and validate resets its workspace to HEAD between runs. It destroyed an uncommitted source edit before anyone noticed. Every command now has its own `--help`, its flags are enumerated, and an unknown flag exits 2 naming it. Validate also prints the workspace and the reset behaviour before it starts, and `bf help` (stale by three commands) lists everything.
- **Fix: `test_provider` reported working tools as unsupported on reasoning models** (#13's misreporting half). The probe capped replies at 16 and 64 tokens, which a reasoning model spends thinking before it emits anything, so the reply came back empty and the tool call never happened. Verified against Gemini 3.1 Pro: with headroom the probe reports `reply: OK` and `tool_calling: ok`. The budget is now 512/2048, and when it is exhausted anyway the report says *that* instead of blaming the tools.
- **Routing: something else picks the model.**
- **A tripwire on what a diff actually did, not on which paths it touched.** Glob rules see paths, not intent: a worker can "fix" a failing test by deleting the assertion, add `.skip`, loosen a guard or drop a `try/catch`, and pass every sensible glob with a green `verify`. Where a `policy.rules` entry with `action: "check"` scopes it, each hunk of the crew's diff now goes to Jev with five typed questions — `test_weakened`, `destructive_data`, `security_touch`, `scope_creep` (Nouls) and `risk` (a Score) — and the probabilities decide `block`, `review` or `allow` per hunk, with the reason recorded. **Additive by construction**: it can add a review or a block and can never remove a glob-triggered one, and it does not run at all until a `check` rule matches, so an install that never asks for it never pays for it. Only `test_weakened` and `destructive_data` can *block* (at `blockAt`, default 0.99) or a `risk` score at `blockRisk` (3.5); `security_touch` and `scope_creep` escalate to a review and no further. Run after `verify` passes — the case it exists for is a green suite over a dishonest diff.
- **Measured, and the miss is recorded rather than tuned away.** `bf bench tripwire` scores 130 labelled diffs (30 planted bad, 100 clean, the clean half deliberately adversarial) against five targets: **measured live against `jev-1.13.0` — recall 90% (27/30) ≥90 ✓, false flags 14% (14/100) ≤10 ✗, of which hard-blocked 0%, clean diffs needing no full review 86% ≥40 ✓, latency 309 ms p50 ≤500 ✓, $0.043 per 1,000 diffs.** By kind: `destructive_data` 100%, `security_touch` 100%, `test_weakened` 86%, `scope_creep` 83%. **The 10% false-flag target is not reachable at any threshold** — a sweep over the recorded answers (so it costs nothing to re-run) finds 100% recall at 39% false flags, 90% at 14%, and 63% at 6%; there is no better point, and pushing stricter collapses recall. The reply-a-review/miss-a-weakened-test asymmetry is why the shipped point leans to recall. Recorded in [docs/tripwire.md](docs/tripwire.md).
- **The tripwire now measures itself against real history, not only against diffs built to fool it.** `bench/make-natural-set.mjs` mines hunks from real commits (capped per commit so one large commit cannot own the corpus) into `bench/tripwire-natural.jsonl` — **175 hunks from 94 real merged commits across 3 repositories**, each carrying its file header so the tripwire sees the path, as it does in production. **Measured live: false flags 4% (7/175), code-only 5%, docs 0%, reviews saved 96%** — the brief's ≤10% target, met. On the game set it stays 14%. The residual flags are not noise: all 7 sit on security-adjacent files (a gateway interceptor, a request guard, a vault grant, a secrets migration, a browser-extension handler) — merged, so false positives by label, but the tripwire is not wrong about what those files are.
- **`reviewRisk` 2.5 → 3.0, a default only the real-diff corpus could have found.** On real diffs `risk` caused **13 of 17 false flags**: ordinary code in a real backend scores 2.5–3.1 on the 0–4 scale, so 2.5 was flagging unremarkable work. Swept against both corpora, 3.0 cuts real-diff false flags 10% → 4% (code 15% → 5%) while costing **nothing** on the seeded set, whose recall stays 90% — only one planted diff depends on a threshold below 3.5 at all. The seeded set could not have revealed this, which is the argument for a second corpus existing.
- **Two ways the bench could report a great number computed from nothing.** A recording that does not cover the set being scored left every row unanswered, and unanswered rows are `allow` — so a wrong `--record` printed a flawless **0% false-flag rate**, indistinguishable from a model that finds nothing. It now refuses with the recording, the set, the count of unanswered rows and the fix. And a corpus with nothing planted no longer prints `recall 0% ... MISS`: it prints `n/a (nothing planted in this set)`.
- **Two defaults the calibration set changed, against the first guess.** **(1)** Gating on the risk Score's confidence flagged **48% of clean diffs** on its own — Jev's confidence there is low on 48% of clean diffs *and* 67% of bad ones, so it separates nothing; `confidenceThreshold` now defaults to `0` (gate off, knob kept). **(2)** `blockAt` 0.8 false-blocked 6 clean diffs while buying **no recall at all** — everything between `reviewAt` and `blockAt` is still reviewed — so it is now 0.99, and false blocks on the calibration set are **zero**. `reviewAt` moved 0.5 → 0.95 for the same reason: a Noul just over half was flagging 51% of the clean set.
- **The tripwire bench could not actually replay offline.** `bf bench tripwire` seeds its TypeSafe double per row from `recorded`, the map it fills *while* a live run records — so on an offline run it seeded nothing, every answer came back blank, every verdict was `allow` and recall was **0%**. That is the worst shape a replay bug can take: a replay that reads nothing is indistinguishable from a model that finds nothing, and it is why the offline arm and the live arm have to be compared rather than assumed equal. It now seeds from the loaded recording, and `test/tripwire-cli.test.mjs` fails on the old code (recall 0%) and passes on the new.
- **A blocked task keeps its evidence.** When the tripwire failed a task, the `verify` result was dropped from the failed entry — losing exactly the fact worth having ("the suite passed and the diff was still blocked"). Failed results now carry `verify`, and the summary line reads `FAILED · verify ok · tripwire BLOCK`.
- **`docs/tripwire.md`**: the decision rule, the threshold table, what it does not do (no rationale, no task context, `allow` is absence of evidence), the three-gate relationship to the plan-level review, and every failure mode (no key, `401`, `429`, timeout, oversized hunk) degrading to a full review rather than a failed plan.
- **Routing: something else picks the model.** `run_plan` and `delegate` now route any task that omits `model`, instead of silently falling back to `defaults.model`. Three engines: `rules` (a deterministic regex table — no key, no network), `jev` (TypeSafe System One, `POST /v1/systemone`), and `off`. **The default is `off`, so nothing changes until you ask for it** — turn it on globally with `routing.engine`, per session with the `routing` parameter on the call, or with `BREAK_FREE_ROUTING=jev|rules|off`. A task with an explicit `model` is never routed. A project `.model-gateway.json` may set `rules` or `off` but **not** `jev`: a cloned repo must never be able to send its own source to a third-party model.
- **Jev decides in one call per plan.** Four typed questions per task (a Choice over lanes, a Score for difficulty, and Nouls for sensitivity and repo context) are answered in parallel in a single request, with probabilities and a confidence per answer. Below `routing.threshold` (default 0.7), or for `lead_keeps`/`unclear`, the task is **not run**: it comes back under "Escalated to you" with its probability distribution, and stays the lead's in the ledger. No key, a `401`, or a malformed body all degrade to `rules` and say so in the result — a router outage never fails a plan. `429`/`529` retry with backoff honouring `retry-after`.
- **Policy runs before any model, and sensitivity is two problems.** File globs (the built-in auth/secrets/`*.pem`/migrations list, `routing.sensitivePaths`, plus your own `policy.rules`) are checked first, so a sensitive task can never be sent to a cheaper lane. `routing.sensitiveLane: "strong"` (default) raises the lane to at least strong, **never lowers it**, and forces an independent review; `"local"` is data residency — everything sensitive stays on this machine.
- **Provenance you can audit.** Task frontmatter gains `routed_by`, `route_lane`, `route_confidence`, `route_probs`, `route_ms` and `overridden_by`; the journal gets one line per decision (`route migration → strong · lane strong confidence 0.88 · sensitive (policy: db/migrations/0031_rate_limit.sql, p=0.93) · by policy in 412ms`). `.break-free/scorecards.jsonl` records one line per executed task with the gateway's own verify result, and the next plan's Jev state quotes them (`migration: fast 0/2 verify pass, strong 1/1`) — the loop that makes a repeatedly-failing lane stop being chosen. `tags` on your plan tasks are the join key.
- **`bf`, the command line.** `bf route --plan …` prints the route table; `bf bench route` scores four routers (lead picks, static rules, Jev, a frontier LLM) against a 60-task labeled set with the guardrails the brief names — agreement, under-routing over free choices, escalation band, latency, and cost against an all-`strong` replay; `bf demo` routes one 12-task plan three ways. Offline by default (a live decision capture replayed through the real client), `--live` for api.typesafe.ai. **Measured against `jev-1.13.0`:** exact lane agreement 71.67% (target ≥80 — missed; 83.67% over the crew lanes a router can actually judge), ±1 tier 100% (≥95 ✓), under-routing 6.98% (≤10 ✓), escalation 10% (10–25 ✓, bottom edge), 12-task plan 1.22 s (≤2 s ✓), $0.000663 per plan (≤$0.001 ✓), 49.4% cheaper than all-`strong` (≥50 — missed by 0.6pt, because `sensitiveLane: "strong"` deliberately upgrades 11 of the 60 tasks). Jev beats static rules on every accuracy measure (71.67% vs 53.33% exact, 6.98% vs 31.03% under-routing), so it is not "just rules" — but rules *look* cheaper (64.1% vs 49.4%) exactly because they under-route three times as often.
- **Two bugs only the live API could expose**, both caught by comparing real decisions with the replay. **(1)** TypeSafe never sends the question key to the model, so `${taskId}__sensitive` told it nothing; with twelve subtasks in one state, a question about "this subtask" was answered about the plan as a whole — every task in a plan containing a migration came back `sensitive`, `difficulty 4`, confidence ~0.5. Every instruction now opens with the state path it is about (`state.tasks[3]`, id and title). **(2)** A 60-task plan exceeded the context (`400 max_tokens_exceeded`) because the questions are not free — a lane question carries all seven option rubrics. `routing.maxRequestTokens` (default 24k) now splits a plan into requests that each fit, which also gives every chunk a smaller, untrimmed state; `route` and `bf` report the request count.
- **Three places to turn routing on or off, all of them yours.** `routing.engine` works at **global** (user config), **project** (`<repo>/.model-gateway.json`) and **session** (the `routing` parameter on a call, or `BREAK_FREE_ROUTING`) level, and the narrower one wins. A project file may now enable `jev` — it is the same egress the file already had through `defaults.model` — and a user who wants every routing decision to stay on their machine sets `routing.projectMayEnableJev: false`, which is read from the user config only so a repo cannot lift its own restriction. Previously a project could not enable `jev` at all; that was inconsistent with `defaults.model` and is now a default-plus-veto.
- **`bf scenarios` — ten real agent workflows, routed four ways.** Ship a feature, fix a flaky test, upgrade a dependency, add auth, chase a performance regression, add CI, split a god-module, add logging, harden the payment path, write a migration guide: 10 plans, 80 tasks, each routed as its own plan through `jev`, `rules`, `off` (no routing) and `lead` (expert). **Measured live against `jev-1.13.0`:** right lane jev 70% / rules 45% / off 25% / lead 100%; **routed below the lane that passes jev 4% / rules 33% / off 45% / lead 0%**; Jev's crew bill 50.5% below all-strong and **20.8% below the expert lead's own picks**; 653 ms per plan for routing, $0.004036 for all ten decision calls. The guardrail line is the story: doing nothing is the most dangerous policy, rules cut it to a third, Jev to a twenty-fifth. Offline runs are reproducible — the recording carries the live latency, and crew cost is priced from the shipped alias/price table so the same run prints the same money everywhere.
- **Tried and reverted: splitting the meta-lanes out of the lane Choice.** `codex_handoff`, `lead_keeps` and `unclear` are not lanes, so they were moved into their own Noul questions, on the theory that they were diluting the distribution over the four real lanes. Mean lane confidence did rise (0.887 → 0.921, so the theory was right) but agreement fell (exact 43/60 → 42/60, crew lanes 41/49 → 37/49) at 50% more questions per task, and a separate "does the user need to decide this?" question could not separate a product decision from a technical design one — the two overlapped across 0.75–0.90 and it fired on design questions the `thinker` lane exists to serve. Reverted; the seven-option Choice stays, and the experiment is recorded in `docs/routing.md` rather than quietly dropped.
- **`cost_report` gains `routing_savings`**: actual crew spend against the same token usage replayed at `strong`'s list price, minus what the routing calls themselves cost (routing spend is logged separately as `route.decision` so it never inflates crew cost).
- **TypeSafe is a `decision` provider, never a chat model.** `PROVIDER_CATALOG` entries now carry `kind: "chat" | "decision"`; `resolveCandidates` skips non-chat providers, so Jev can never be selected as a worker. `test_provider typesafe` probes the real endpoint.
- **Fix: `globToRegex` rewrote its own output.** It applied its replacements in a chain, so the directory group it inserted for a `**/` prefix was itself re-escaped into `(.[^/]*/).` — every `**`-prefixed glob silently failed to match a real path. Deny rules, review rules and routing sensitivity all read globs through that one function, so all three were affected. Replaced with a single-pass translator, with the cases pinned by tests.
- **Fix: a log field could overwrite the event kind.** `log(kind, fields)` spread `fields` over `kind`, so passing a `kind` field renamed the event; the routing summary events were invisible to `cost_report` and `gateway_logs` as a result.

## 3.4.0 — 2026-09-18
- **CI and deployments are blocking work.** A successful `git_push` or `gh_merge_pr` enqueues a `ci.pending` event for that commit, and the watcher resolves it by asking `gh` for the run's conclusion, in shell rather than through a model. Success drains silently; failure becomes a blocking `ci.failed` carrying the run URL and failing job, so the turn-end guard will not let the turn end on top of it. A green workflow is not treated as a healthy deploy: where the commit has deployments, their own status must succeed too. Bounded by `fleet.ciTimeoutMs` (20 minutes) and fully inert when `gh` is missing or unauthenticated, so an unverifiable run can never wedge a session.
- **Event-driven fleet supervision.** `src/fleet.ts` turns a snapshot diff (job states, harness pane digests) into actionable wake events on a durable append-only queue, with the drain cursor in a separate file so a crash between appending and draining cannot lose a wake-up. `fleet_status` exposes it; `--fleet-check` prints the same object and always exits 0.
- **Turn-end guard.** The installer now writes exactly one Claude Code `Stop` hook calling `--fleet-check --hook`, so the lead cannot silently end a turn while delegated work is still running. In hook mode the CLI prints a block decision when the fleet is busy, nothing at all when it is settled, always exits 0, and never writes to stderr. `--uninstall` removes it and leaves unrelated hooks intact; `--doctor` reports whether it is installed.
- **Crew aliases.** `ensign`, `commander`, `counselor`, `holodeck` and `subspace` resolve to the same chains as `fast`, `strong`, `reviewer`, `local` and `cloud`. Both names work. A crew alias points at the core alias by name, so it follows whatever that alias means at resolution time, including a user override; a regression test pins that.
- **Named project modes.** `mode` is one of `guarded` (default), `pr-only` or `local-only`, with `mergeAutonomy` as a separate opt-in. It derives `github.allowPush` / `github.allowMerge`, applied only where the raw config did not set them explicitly, so an explicit value still wins and every existing enforcement point picks the mode up unchanged. `mode` and `mergeAutonomy` are unreachable from an untrusted project `.model-gateway.json` (the sanitiser is an allowlist).
- **BREAKING: merge autonomy is now opt-in.** `github.allowMerge` previously defaulted to `true`, so a worker holding the `github` capability could merge a PR out of the box. Under `guarded` it now defaults to `false` unless `mergeAutonomy` is set. Push behaviour is unchanged. Set `"mergeAutonomy": true` to restore the old behaviour.
- **Scout task shape.** `shape: "ship" | "scout"` on `delegate`, `supervise` and `run_plan` tasks. A scout has its capabilities forced to `read` regardless of what was requested, and reports that it changed nothing — a read-only investigation with an obvious name instead of a hand-written capability list.
- **Visible crew.** `harness_spawn`, `harness_status` and `harness_list` return an `attach` command, so a tmux sub-agent can be watched or typed into rather than only read through `harness_read`.
- Install: `install.sh` works standalone — `curl -fsSL .../install.sh | bash` clones (or fast-forwards) `~/.break-free` (`BREAK_FREE_HOME`, `BREAK_FREE_BRANCH`), checks Node 20+ **before** writing anything, re-attaches `/dev/tty` so the interactive installer still prompts under a pipe, and passes flags through (`| bash -s -- --yes`).

Reference material moved below.

- Distribution: no CI on this repo — install and update directly from GitHub. `setup.mjs --update` (and `/break-free-update`) self-update from a `git clone` (`git pull --ff-only` + hands-free re-install), reusing the scope/agents recorded in `last-install.json`.
